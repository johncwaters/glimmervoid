# Sketch

Give the questions something concrete to attack.

1. Name the repo. `<repo>` is `basename "$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")"`, the main checkout's name from any worktree; outside git, the working directory's name.
2. Resume the design spec in `~/.local/state/ship/specs/<repo>/` whose request and goal match this feature, once the operator confirms the match, and set its `repoRoot` to the current checkout; a `challenged` one with a different request is a different feature. A new feature gets `<slug>.json`: two to five kebab-case words, new to that directory.
3. Read the repo and beyond it: instruction files, prior art by behavior and synonym in the repo and, through WebSearch and WebFetch, in official docs and established projects, the code the feature touches, and `git log -20` on those paths for the decisions behind it. Record what the repo settles as decisions with source `read` and their `evidence`: the path:line, commit sha, or backticked command that showed it, so a fact about an outside system cites the probe that showed it rather than a code line that does not prove it. For a bug, trace the defect to the layer that owns it, through `git log` or a bisect when it used to work, and record it as a `read` decision with evidence, even when the code nearest the symptom looks like the obvious place for the fix; only a trace ending at two plausible owners becomes a branch.
4. Write the graph at status `sketch`: `request`, `repoRoot`, the goal with its `problem` and `upstream`, the non-goals, the `read` decisions, and one branch per guess with its leaning and its `upstream`, each joined by a `blocks` edge to the branches it precedes. The goal's `problem` says who is blocked and what they cannot do today, in the operator's terms and free of any mechanism; the goal's `text` states the outcome the same way. A request that names a solution has it recorded as the first branch, its leaning the named solution, with a `blocks` edge to every other branch, so the question rounds weigh it against alternatives before anything under it. A branch's `upstream` says what one level up would make its question unnecessary (did this work before, should the thing exist or be shared at all, is a caller misusing it) and cites what you read to weigh it: a path:line, a commit sha, or a backticked command. Write `none: <reason>` only for a choice nothing sits above, such as a name or behavior that does not exist yet; an upstream that settles the question is a `read` decision, not a branch. The goal's `upstream`, written before any branch, names the simplest trigger and source one level up that would remove the most branches, cited the same way, or `none: <reason>` for a feature nothing sits above.
5. Tell the operator the problem and the goal as understood and the branch count, then continue to `grill.md`.
